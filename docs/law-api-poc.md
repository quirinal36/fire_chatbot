# 법령 API 연결 시험 결과 (ISS-003)

원본: [기획서 §4.1~4.3](../소방시설_법령_API_챗봇_프로그램_기획서.md) · 이슈: [#3](https://github.com/quirinal36/fire_chatbot/issues/3) · 시험일: 2026-09-17

재실행: `node scripts/law-api-poc.mjs` (`.env` 의 `API_AUTHKEY` 필요). 인증값을 제거한 응답 샘플은 [`tests/fixtures/law-api/`](../tests/fixtures/law-api/)에 있다.

## 결론

신청·권한은 유효하다. 5개 target 모두 HTTPS·JSON 으로 응답했고 §4.3 의 1~5 단계를 통과했다. 6단계(Vercel Preview 동일 시험)는 배포 전이라 미수행이다.

18개 계약 검사 중 16개 통과. 실패 2건은 아래 **발견 사항**에 적는다.

| 단계 | 대상 | 결과 |
|---|---|---|
| 목록 | `eflaw` (`nw=3`, `search=1`) | 통과 · totalCnt 3 |
| 본문 | `eflaw` `ID=009694` | 통과 · 227,578 bytes |
| 본문 | `eflaw` `MST=287375` + `efYd=20260701` | 통과 · ID 조회와 동일 바이트 |
| 목록 | `admrul` (`nw=1`) | 통과 · totalCnt 3 |
| 본문 | `admrul` `ID=2100000273566` | 통과 · 15,154 bytes |
| 목록·본문 | `nfaCgmExpc` | 통과 · totalCnt 139 |
| 검색 | `licbyl` (`search=2`) | 통과 · totalCnt 10 |
| 검색 | `admbyl` | 통과 · totalCnt 7 |

응답 지연은 115~780ms 였다.

## 성공·실패 판정 계약

`HTTP 200` 만으로 성공이라고 판단하면 안 된다. 인증이 틀려도 **200 으로 온다.**

```json
{ "result": "사용자 정보 검증에 실패하였습니다.",
  "msg": "OPEN API 호출 시 사용자 검증을 위하여 정확한 서버장비의 IP주소 및 도메인주소를 등록해 주세요." }
```

기획서 §4.3 은 오류가 HTML 로 올 가능성을 경계했는데, 실제로 확인된 형태는 **JSON 오류 본문**이다. HTML 방어는 그대로 두되 아래를 순서대로 검사한다.

1. `res.ok`
2. HTML 여부 (`<!doctype` / `<html` 로 시작)
3. `Content-Type` 에 `json` 포함
4. `JSON.parse` 성공
5. `result` + `msg` 키가 있으면 **오류** (성공 응답에는 없다)
6. 목록은 `resultCode === "00"`

샘플: [`error-invalid-oc.json`](../tests/fixtures/law-api/error-invalid-oc.json)

## 발견 사항

### 1. 목록 응답의 상세링크에 인증값이 그대로 담겨 온다 — P0

5개 target **전부** 해당한다.

```
/LawSearch/law[]/법령상세링크          → /DRF/lawService.do?OC=<OC>&target=eflaw&MST=287375&...
/AdmRulSearch/admrul[]/행정규칙상세링크 → /DRF/lawService.do?OC=<OC>&target=admrul&ID=...
/CgmExpc/cgmExpc[]/법령해석상세링크     → /DRF/lawService.do?OC=<OC>&target=nfaCgmExpc&ID=...
/licBylSearch/licbyl[]/별표법령상세링크  → /DRF/lawService.do?OC=<OC>&target=licbyl&ID=...
/admRulBylSearch/admrulbyl[]/별표행정규칙상세링크 → /DRF/lawService.do?OC=<OC>&target=admbyl&ID=...
```

기획서 §9 는 "원천 API 쿼리에 들어간 OC 를 로그에서 제거한다"고만 규정한다. 그런데 OC 는 **응답 데이터에도** 들어 있으므로 로그 마스킹만으로는 부족하다.

- 이 필드를 `legal_versions.source_url` 에 그대로 저장하면 DB 에 키가 남는다.
- 근거 카드로 브라우저에 내려가거나 모델 프롬프트에 들어가면 키가 외부로 나간다.

**수집 시점에 제거한다.** `scripts/law-api-poc.mjs` 의 `stripOC()` 가 참고 구현이다. 저장용 URL 은 §6.3 대로 서버가 DB 값으로 다시 조립한다. ISS-005 · ISS-006 에 반영이 필요하다.

### 2. 소방청 해석의 `이유` 가 비어 있다 — P1

`nfaCgmExpc` 본문에서 `질의요지` 와 `회답` 은 채워지지만 `이유`, `안건번호`, `해석일자`, `질의기관명` 은 빈 문자열이다. 기획서 §4.3-5 는 "질의요지·회답·이유를 확인한다"를 조건으로 두는데 `이유` 는 이 target 에서 제공되지 않는 것으로 보인다.

표본이 1건이므로 여러 건을 더 확인해야 한다. 해석을 근거로 쓸 때 `이유` 가 없다는 전제로 설계하거나, 상세링크(HTML) 를 별도 수집해야 한다. ISS-024 에서 확정한다.

## 어댑터 설계에 반영할 계약 차이

기획서 §4.1 의 "동일한 파서로 처리할 수 있다고 가정하지 않는다"가 실물로 확인됐다.

| 항목 | 법령 (`eflaw`) | 행정규칙 (`admrul`) |
|---|---|---|
| 현행 구분값 | `nw=3` | `nw=1` |
| 루트 키 | `법령` | `AdmRulService` |
| 목록 루트 키 | `LawSearch` | `AdmRulSearch` |
| 조문 | `조문.조문단위[]` (63) | `조문내용[]` (16, 문자열 배열) |
| 별표 | `별표.별표단위` = **배열** (10) | `별표.별표단위` = **단일 객체** |
| 첨부 | 별표 항목의 `별표서식파일링크` | `첨부파일.첨부파일링크[]` |
| 식별자 | `법령ID` + `법령일련번호`(MST) | `행정규칙ID` + `행정규칙일련번호` |

추가로 확인한 것:

- **별표번호는 `"0004"` 형태의 4자리 제로패딩 문자열**이다. 숫자로 비교하면 못 찾는다.
- **별표 본문이 법령 본문 호출에 함께 온다.** 시행령 별표 4 는 439줄·28,090자로 전문이 들어 있어, HWP 다운로드 없이도 구조화할 수 있다. 기획서 §4.4 는 별표를 별도 다운로드 대상으로만 다뤘다.
- 시행령 별표 번호와 기획서 §4.1 의 전제가 일치한다. 별표 2 특정소방대상물, **별표 4 소방시설의 종류**, 별표 5 면제 기준.
- **별표 본문은 고정폭 공백 정렬 + 괘선문자(`┌─┬─┐`) 표**이며 단어 중간에서 줄이 끊긴다(`다음의 어` / `느 하나에`). §4.4 의 `needs_review` 게이트가 자주 발동할 것으로 본다. ISS-008 의 난도를 낮게 잡지 않는다.
- **`조문단위[].항` 의 형태가 일정하지 않다.** 63개 조문 중 항 없음 25, 단일 객체 13, 배열 25. `호` 도 같다. 런타임 스키마에서 단일 객체를 1개짜리 배열로 정규화한다.
- **별표 검색의 기본 `section` 은 별표명(`bylNm`)** 이다. 법령명으로 찾으려면 `search=2` 를 넘긴다. 이걸 빼면 `totalCnt: 0` 이 조용히 돌아온다.
- 별표 파일링크는 법령이 **상대경로**(`/LSW/flDownload.do?flSeq=...`), 행정규칙 첨부는 **절대 URL 이지만 `http://`** 다. §4.4 대로 공식 호스트 기준으로 해석하고 HTTPS 로 올린다.

## 배포 환경 시험 (§4.3-6) · 2026-09-17

`GET /api/diagnostics/law-api` (서버 `server/`, `DIAGNOSTICS_TOKEN` 필요)로 Vercel 함수에서 `eflaw`·`admrul` 목록을 호출했다.

| 실행 위치 | 송신 IP | eflaw | admrul |
|---|---|---|---|
| 로컬 개발 | 106.243.26.78 | 734ms | 732ms |
| Vercel `iad1` (미국 동부) | 3.236.237.195 | 334~1,140ms | 323~1,118ms |
| Vercel `icn1` (서울) | 13.209.4.168 | 151~261ms | 140~754ms |

**세 위치 모두 정상 응답했다.** 등록하지 않은 송신 IP에서도 인증이 통과하므로 현재 신청 상태에서는 IP 등록이 필요하지 않다. 고정 송신 IP 환경은 두지 않는다. 서버 함수 리전은 `icn1`로 고정했다(`server/vercel.json`).

- 이 시험은 Production 환경으로 했다. main 푸시가 곧 Production 배포이기 때문이다. Preview는 같은 환경변수·같은 리전이라 결과가 같다고 본다.
- 운영기관이 나중에 IP 검증을 켤 수 있다. 수집 작업의 인증 오류 알림(ISS-023)에서 `api_error`와 `msg`를 그대로 보고하게 해 바로 알아차리게 한다.
