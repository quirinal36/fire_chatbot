# GitHub 마일스톤 계획

기준 문서: [소방시설 법령 API 챗봇 프로그램 기획서 v0.1](../소방시설_법령_API_챗봇_프로그램_기획서.md) · 작성일: 2026-09-17

이 문서는 GitHub Milestones의 제목·설명·완료 조건을 정의한다. 마일스톤 8개와 이슈 32개의 실제 등록을 완료했다. 실제 번호와 링크는 [GitHub 등록 결과](github-registration.md), 이슈 본문은 [이슈 백로그](github-issues.md)를 확인한다.

## 일정 및 운영 원칙

- 8주·1인 개발은 기획서의 일정 초안이다. 착수일과 수행 약정이 확정되기 전에는 GitHub due date를 지정하지 않는다.
- `M1`~`M8`, `ISS-001`~`ISS-032`는 문서상의 추적 ID이며 실제 GitHub 이슈 번호가 아니다. 등록 후 실제 번호와 의존 링크를 연결한다.
- 모든 마일스톤과 이슈의 초기 상태는 계획이다. 담당자와 검토자는 착수 시 지정한다.
- P0는 출시 또는 다음 단계 진행에 필수, P1은 1차 제공 범위의 보완 작업이다. P1도 임의로 제외하지 않으며 범위 변경을 기록한다.
- 공통 완료 조건: 해당 이슈의 체크리스트 충족, 필요한 검증 결과와 산출물 링크 기록, 관련 문서 갱신. 법령 판단의 정답과 규칙은 소방 담당자가 승인한다.
- 4주차 검색 챗봇을 첫 제품 검토 지점으로 삼는다. 규칙 승인이 늦으면 검색 기능을 우선 제공하고 미승인 판정을 공개하지 않는다.
- 전 업종 자동 판정, 도면 분석·수량 산출, 건축물대장 연계, 공적 증명서 발급, 복잡한 이력 자동 해석 및 범용 규칙 편집기는 이번 백로그에서 제외한다.

## M1 · 착수 결정 및 외부 연동 PoC

설명: 최초 업종·시설, 검토 담당자, 자료 정책, 예산 및 운영 환경의 결정 항목을 관리하고 법령 API·OpenRouter 연동 가능성을 검증한다. 참조: 기획서 §1, §4.1~4.3, §9, §12, §14.

완료 조건:
- [ ] 공개 법령 기반 PoC 범위와 영구 ID 수집 목록 초안이 있다.
- [ ] 법령·NFPC·NFTC·별표 원문과 소방청 해석 응답을 확보하고 개발/Preview 연결 결과를 기록했다.
- [ ] 모델 JSON 응답·임베딩 연결을 확인하고 DB·환경 설정 초안을 작성했다.
- [ ] 미확정 항목마다 결정 담당자·기한·차단 범위를 기록했다. 미확정 항목을 승인 완료로 취급하지 않는다.

## M2 · 법령 수집 및 버전 저장

설명: 원문 저장, target별 파싱, 문서 구조와 버전 보존을 구현한다. 참조: 기획서 §4.4~4.5, §5, §13.

완료 조건:
- [ ] 선정 문서의 본문·부칙·필수 별표를 저장하고 수집 누락을 대조했다.
- [ ] 재실행 시 동일 버전 중복 저장과 불필요한 재임베딩을 방지한다.
- [ ] 현행·시행예정·연혁을 구별하고 구버전을 보존한다.
- [ ] 불완전한 표는 검토 대기로 표시되어 자동 판단 근거 게시에서 제외된다.

## M3 · 근거 검색 및 검색 평가

설명: 정확 일치·키워드·벡터 검색을 결합하고 근거 조회와 평가 데이터 기반을 만든다. 참조: 기획서 §5, §6.1, §10.

완료 조건:
- [ ] 문서·질의 임베딩 모델과 차원이 일치하며 버전·공개 범위를 검색 전 강제한다.
- [ ] 근거 조항과 상위 문맥·비고·연결 예외를 함께 조회한다.
- [ ] 담당자 검토 질문 50건 이상의 평가셋과 Recall@10 기준 측정 결과가 있다.
- [ ] 검색 실패 유형과 개선 이슈를 기록했다. 최종 90% 목표 검수는 M7에서 수행한다.

## M4 · 근거 검색 챗봇 MVP

설명: 법령 질문에 근거를 검색하고 검증된 답변만 표시한다. 참조: 기획서 §2, §6.2~6.4, §8.

완료 조건:
- [ ] 질문 → 검색 → 생성 → 검증 → 인용 카드의 수직 흐름이 동작한다.
- [ ] 인용 ID·스키마를 검증하고 URL은 DB에서 구성한다.
- [ ] 검증 실패 시 1회 재시도 후 근거와 추가 확인 안내를 반환한다.
- [ ] 상태 SSE와 검증된 최종 답변만 전달하며 검색 결과 부재를 비해당으로 표시하지 않는다.
- [ ] 첫 제품 검토 결과와 후속 수정 항목을 기록했다.

## M5 · 영업장 조건 및 검토된 판단 규칙

설명: 제안 업종인 일반음식점 또는 확정 업종에서 입력 확인과 승인된 규칙 실행을 연결한다. 참조: 기획서 §6.2, §7, §8.

완료 조건:
- [ ] 입력 후보·사용자 확인·미확인 상태와 사건 날짜를 관리한다.
- [ ] 조건 변경 시 revision 증가와 판단 캐시 무효화가 동작한다.
- [ ] 승인 규칙만 해당/비해당을 만들고 미지원·미확인 범위는 추가 확인으로 처리한다.
- [ ] 담당자 선정 경계값·예외·누락 사례에서 판단 경로를 재현했다.

## M6 · 관리자 검토 및 개정 갱신

설명: 승인·반려·감사 이력, 개정 영향 분석, 중단 후 재개 가능한 예약 수집을 구현한다. 참조: 기획서 §4.5, §8, §9.

완료 조건:
- [ ] 관리자 수집 실행·실패 재처리·문서 비교·문서 및 규칙 승인이 가능하다.
- [ ] 새 버전 발견 시 영향 규칙을 검토 대기로 전환하고 자동 판단을 추가 확인으로 낮춘다.
- [ ] Cron 중복 실행·실행시간 종료·lease 만료 후에도 중복 게시 없이 재개한다.
- [ ] 내부 자료 공개 승인과 외부 모델 전송 승인을 별도 집행한다.

## M7 · 통합 검증 및 운영 안정화

설명: 기획서의 검수 기준을 측정하고 주요 결함을 수정한다. 참조: 기획서 §6.4, §9~10, §12.

완료 조건:
- [ ] 타 세션·내부 문서·관리자 API 접근을 차단하고 비밀값 로그 노출이 없다.
- [ ] 429·인증 실패·잘못된 JSON·수집 중단·모델 실패 복구를 확인했다.
- [ ] Recall@10 90% 이상, 규칙 경계·예외 전부 일치, 잘못된 인용 및 규칙 충돌 0건을 검수 사례에서 확인했다.
- [ ] 측정 환경·표본을 기록하고 최종 답변 p95 20초 목표 달성 여부를 보고했다.
- [ ] 100개 질문 비용 측정 및 월 1,000/10,000/50,000회 예상 비용을 작성했다.

수치 목표는 담당자와 조정 가능하나, 변경 이유·승인자·변경값을 기록한다. 미달 항목은 자동으로 완료 처리하지 않는다.

## M8 · 운영 배포 및 인수인계

설명: 운영 정책·환경·복구·사용 설명·최종 검수를 완료한다. 참조: 기획서 §9~12, §14.

완료 조건:
- [ ] 운영 계정·도메인·자료 정책·저장기간·비용 상한·유지보수 범위가 확정되었다.
- [ ] 운영 배포와 핵심 흐름 점검, 백업 복원 및 롤백 절차 검증을 마쳤다.
- [ ] 사용자·관리자 안내서 및 수집/개정/장애 대응 문서를 전달했다.
- [ ] 담당자 최종 검수 결과와 실제 지원 업종·시설·규칙 버전을 기록했다.

## GitHub 등록 방법

1. 위 표의 제목으로 마일스톤 8개를 만들고 각 설명·완료 조건을 description에 넣는다.
2. 이슈 문서의 제목과 본문을 복사해 이슈를 만들고 지정 milestone과 labels를 연결한다.
3. 선행 작업의 문서 ID를 실제 GitHub 이슈 링크로 교체한다. `없음`인 이슈는 독립 착수 가능하다.
4. 검토가 필요한 이슈에 결정 담당자와 검토자를 지정한다. 실제 일정 확정 후 due date를 넣는다.
5. 각 이슈의 검증 증거를 남기고 종료한 뒤 마일스톤 완료 조건까지 확인한다.
