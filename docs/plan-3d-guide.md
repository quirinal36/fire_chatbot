# 2D 도면 → 3D 벽 기능 구현 안내

대상 독자: 다른 프로젝트에 이 기능을 옮겨 붙이려는 개발자.

사진이나 이미지로 올린 2D 평면도에서 벽을 찾아 브라우저 안에서 3D로 세우고, 벽을 긋고 지우고, 축척을 맞춰 방 면적을 재고, 시각 LLM으로 결과를 보완하는 기능이다. 이 저장소의 구현은 `frontend/src/plan/`과 `server/src/lib/plans.ts`·`plan-review.ts`·`plan-scale.ts`에 있다. 이 문서는 그 구현을 다른 스택에서 다시 만들 수 있을 만큼의 절차와 수치, 그리고 우리가 실제로 밟은 함정을 적는다.

CAD 파일(DWG/DXF) 없이 **래스터 이미지만** 가지고 한다. 서버나 설치형 프로그램(Rhino, AutoCAD) 없이 브라우저에서 처리한다.

## 1. 전체 구조와 이식 난이도

기능을 네 층으로 나눈다. 아래로 갈수록 이식 비용이 커진다.

| 층 | 역할 | 의존성 | 줄 수 | 이식성 |
|---|---|---|---|---|
| 1. 벽 추출·편집 | 이미지 픽셀 → 벽 마스크 → 다각형 | 없음 (순수 TS) | 약 850 | 그대로 복사 |
| 2. 방·개구부 | 마스크 → 방 면적, 문·창 자리 | 1층만 | 약 250 | 그대로 복사 |
| 3. 3D 뷰어 | 다각형 → 화면, 마우스 편집 | Three.js | 약 360 | Three.js 쓰면 그대로 |
| 4. UI·저장·AI | 화면 조립, 계정 저장, LLM 검토·축척 | 프레임워크·백엔드·LLM | 약 1,500 | 다시 씀 |

1·2층은 DOM을 쓰지 않는다. `Uint8ClampedArray`(RGBA)를 받아 `Uint8Array`(마스크)와 좌표 배열을 돌려주는 순수 함수뿐이다. 그래서 Node에서 단위 시험이 되고, React·Vue·Svelte·Next.js 어디에도 그대로 들어간다. 이식할 때 **1·2층은 파일째 복사하고 3·4층만 다시 쓰는 것**을 권한다.

파일 구성은 이렇다.

```
plan/
  walls.ts      약 700줄  이진화·두께 추정(두 봉우리)·모폴로지·끊긴 벽 잇기·빗금 내벽 보조 추출·경계 추적·단순화·편집 함수
  rooms.ts      약 230줄  건물 윤곽 판정, 개구부 후보를 막아 방 나누기, 면적
  openings.ts   약 260줄  개구부 후보 찾기 (행·열 스캔 + 벽 끝점)
  viewer.ts     388줄  Three.js 뷰어 (동적 import)

server/lib/
  plan-review.ts       검출 결과를 시각 LLM 에 보여 주고 고칠 곳을 받는다
  plan-scale.ts   294줄  치수선을 읽어 축척을 확정한다 (사슬 계산은 순수 함수)
```

## 2. 핵심 설계 결정: 벽 마스크를 단일 원본으로 둔다

이 구현의 중심은 **`Uint8Array` 벽 마스크 하나**다. 픽셀당 1바이트로 벽이면 1, 아니면 0이다. 이미지와 같은 크기다.

모든 동작이 이 마스크를 거친다.

- 추출: 이미지 → 마스크
- 벽 추가: 마스크에 칠하기
- 벽 지우기: 마스크에서 비우기
- 3D: 마스크 → 다각형 → 압출
- 방 면적: 마스크에서 방 찾기
- 저장: 마스크를 1비트 PNG로
- AI 검토: 마스크를 빨간 반투명으로 원본에 겹쳐 전송

벡터 선분 목록(시작점·끝점·두께)을 상태로 두는 설계도 가능하지만 권하지 않는다. 래스터 도면에서 뽑은 벽은 선분으로 깔끔하게 떨어지지 않고, 교차·병합·분할 처리가 전부 기하 코드가 된다. 마스크는 그 모든 것이 그냥 픽셀 덮어쓰기다. 되돌리기도 `mask.slice()` 한 줄이다.

대가는 메모리다. 1600×1131 도면이면 마스크 1.8MB, 되돌리기 20단계면 36MB다. 브라우저에서는 문제없는 수준이지만, 되돌리기 한도를 두어야 한다(우리는 20).

```ts
// 되돌리기: 스냅샷 방식
function pushUndo(): void {
  undo.push(mask.slice());
  if (undo.length > UNDO_LIMIT) undo.shift();
}
```

## 3. 벽 추출 절차

### 3.1 전처리

**축소.** 긴 변을 1600px로 줄인다. 원본이 7000px인 도면도 있고, 모폴로지 연산은 픽셀 수에 비례한다. 1600px면 벽 두께가 6~25px로 잡혀 충분하고 전체 처리가 1초 안에 끝난다.

**흰 바탕 채우기.** 캔버스에 흰색을 먼저 칠하고 그 위에 그린다. PNG의 투명 배경이 검정으로 읽혀 전체가 벽이 되는 사고를 막는다.

```ts
const scale = Math.min(1, 1600 / Math.max(bitmap.width, bitmap.height));
canvas.width = Math.round(bitmap.width * scale);
canvas.height = Math.round(bitmap.height * scale);
const ctx = canvas.getContext('2d', { willReadFrequently: true });
ctx.fillStyle = '#fff';
ctx.fillRect(0, 0, canvas.width, canvas.height);
ctx.drawImage(bitmap, 0, 0, canvas.width, canvas.height);
const pixels = ctx.getImageData(0, 0, canvas.width, canvas.height);
```

`willReadFrequently: true`를 빼면 `getImageData`가 GPU→CPU 전송을 매번 해서 눈에 띄게 느려진다.

### 3.2 이진화

밝기가 기준보다 어두운 픽셀을 "선"으로 본다. 밝기는 NTSC 가중치(299:587:114)를 쓴다.

**기준값은 160을 권한다.** 처음에 110으로 했다가 회색 벽(밝기 126)으로 그린 도면에서 벽을 전부 놓쳤다. 160이면 검정 벽(0~50)과 회색 벽(126)을 모두 잡고, 흰 바탕(255)과 연한 격자·해치(191, 230)는 버린다. 알파가 128 미만인 픽셀은 흰 바탕으로 본다.

이 값은 사용자가 조절할 수 있게 열어 두어야 한다. 스캔 도면이나 손그림은 다른 값이 맞다.

### 3.3 벽 두께 추정

벽 두께를 알아야 다음 단계의 커널 크기가 정해진다. 학습 없이 런 길이 분포로 추정한다.

가로·세로 모든 줄에서 연속된 어두운 픽셀의 길이(런 길이)를 센다. 세로 벽은 가로 방향 스캔에서 "두께 길이"의 런을 벽 높이만큼 많이 만들고, 가로 벽은 세로 방향에서 그렇다. 그래서 **길이 × 등장 횟수**가 가장 큰 길이가 벽 두께다. 단순 최빈값을 쓰면 1px(글자·가는 선)이 이겨 버린다.

```ts
const bump = (len: number) => { if (len >= 2 && len <= 64) score[len] += len; };
// 모든 행과 모든 열에서 런을 세고 bump
// score 가 최대인 len 이 벽 두께
```

실제 값: 기본 사무실 도면 23px, 카카오톡 평면도 6px, 합성 시험 도면 10px. 전부 정확히 맞았다.

### 3.3.1 벽이 두 가지로 그려진 도면 — 빗금 내벽

두께를 하나만 잡으면 무너지는 도면이 흔하다. **외벽은 짙게 채우고 내벽은 빗금(해치)으로 채우는** 도면이다. 한국 아파트 평면도가 대체로 이렇다.

빗금 내벽은 속이 찬 띠가 아니다. 가는 선 두 줄 사이에 사선이 성긴 간격으로 그어져 있을 뿐이다. 그래서 가로로 자르면 1~3px짜리 런만 나오고, 두께 투표에 제 두께로 참여하지 못한다. 짙게 채운 외벽이 압승한다.

결과가 조용히 나쁘다. 실제 아파트 도면에서 두께가 27px로 잡히고 열림 커널이 16px이 되어, **내벽이 통째로 지워지고 외벽만 남았다.** 방이 하나도 나뉘지 않는다.

사용자가 두께 슬라이더를 5px로 내리면 내벽이 살아나지만, 이번에는 가구와 글자까지 남고 (6.3절의) 축척 가정이 5배 틀어진다. 실제로 거실 면적이 440㎡로 나왔다.

**닫힘을 먼저 걸어 빗금의 속을 채운 뒤 두께를 다시 재면 해결된다.**

```ts
const coarse = estimateThickness(binary, w, h);        // 27 — 외벽만 보인다
const solid = morphClose(binary, w, h, hatchKernel(coarse)); // 커널 7 — 빗금이 메워진다
const { thick, thin } = estimateThicknessModes(solid, w, h); // { thick: 27, thin: 9 }
```

닫힘 커널은 굵은 두께의 0.25배(3~9px로 제한)다. 빗금 간격은 벽 두께에 따라 커지므로 비례해 잡되, 더 키우면 가구 선까지 메운다.

두 번째 봉우리는 이렇게 찾는다. 굵은 두께의 1/1.6 이하 구간에서 다시 최다 득표를 뽑고, 득표가 굵은 쪽의 15% 이상일 때만 인정한다.

**여기에 하한이 하나 더 필요하다. 4px보다 얇으면 벽 표현으로 보지 않는다.** 이 조건이 없으면 선으로만 그린 도면에서 무너진다. 1~3px짜리 런은 어느 도면에나 널려 있다 — 글자 획, 가구 윤곽, 치수선, 안티에일리어싱. 실제 주택 평면도(벽 6px)에서 2px가 "얇은 벽"으로 뽑혔고, 열림 커널이 3으로 내려가 **걸러 내는 일을 아예 안 하게 됐다.** 그 도면은 가구가 벽으로 잡히고 구역이 5개밖에 안 나뉘었다.

굵은 벽이 6px 남짓인 도면에서는 이 하한 때문에 두 번째 봉우리가 아예 나올 수 없다. 그래도 된다. 그 해상도에서 구별되는 벽 표현이 두 가지일 수는 없다.

**그다음이 중요하다. 열림은 얇은 쪽에 맞추고, 축척 가정은 굵은 쪽으로 한다.**

```ts
const t = thin ?? thick;                     // 열림 커널은 얇은 벽이 살아남게
const mask = openAt(solid, w, h, t, minArea);
return { mask, wallPx: thick, thinPx: thin }; // 축척 가정은 외벽 두께로
```

두께 하나가 두 가지 일(열림 커널, 축척 가정)을 겸하면 안 된다. 겸하게 두면 사용자가 두께를 내렸을 때 도면이 조용히 커진다.

작은 덩어리 문턱도 달라진다. 두께가 하나면 `두께² × 4`지만, 두 가지면 `얇은두께 × 굵은두께 × 2`를 쓴다. 얇은 벽도 길이는 굵은 벽만큼 나오므로, 그 정도 넓이가 안 되면 가구·글자로 본다.

### 3.4 모폴로지 열림 — 이 단계가 핵심이다

침식 다음 팽창을 한다. 커널 크기는 **벽 두께의 0.6배**(홀수로 맞춤)다. 그보다 얇은 것은 어느 방향으로도 통째로 사라지고, 두꺼운 벽은 원래 두께로 돌아온다.

이 한 단계가 글자, 가구 윤곽, 문 호(arc), 치수선, 창문 이중선, 계단 디딤판, 해치 무늬를 전부 지운다. 규칙 기반 필터를 여럿 만들 필요가 없다.

0.6이라는 비율은 시험으로 얻었다. 너무 크면 벽 모서리가 깎이고, 너무 작으면 두꺼운 가구가 남는다.

**구현은 분리 가능(separable) + 누적합으로 한다.** 2차원 커널을 그대로 돌리면 O(N·k²)이고, 벽 두께가 25px인 도면에서 커널이 15×15가 되어 체감으로 느려진다. 가로 1차원 → 세로 1차원으로 나누고, 각 방향에서 슬라이딩 창 안의 1 개수를 누적합으로 구하면 커널 크기와 무관하게 O(N)이다.

```ts
// 한 방향 침식/팽창. prefix[i+1] - prefix[a] 로 창 안의 1 개수를 센다
const ones = prefix[b + 1] - prefix[a];
out[idx(i)] = erode ? (ones === k && b - a + 1 === k ? 1 : 0) : ones > 0 ? 1 : 0;
```

침식에서 경계 밖은 0으로 본다(`b - a + 1 === k` 조건). 이미지 가장자리에 걸친 벽이 깎이는 문제는 뒤의 함정 절에서 다룬다.

### 3.4.1 끊긴 벽 잇기와 연한 빗금 벽 보조 추출

열림을 거치면 성긴 빗금 내벽이 점선처럼 토막 난다. 그러면 방 나누기가 그 틈으로 새어 두 방이 하나가 된다. **가로·세로 한 방향씩만 닫는 닫힘(`bridgeGaps`)** 으로 같은 줄 위의 좁은 틈만 메운다. 커널은 얇은 벽 두께의 3배(최대 31px)다. 2차원 닫힘과 달리 모서리를 뭉개지 않고, 원래 픽셀은 그대로 두고 더하기만 하므로 가장자리가 깎이지 않는다. 문·창은 벽 두께의 몇 배라 메워지지 않는다.

한국 아파트 도면의 빗금 내벽은 대개 **연한 회색(밝기 160~220)** 이라 기본 이진화(160)에서 대부분 버려진다. 실제 도면에서 침실 사이 벽이 이렇게 사라져 침실 둘과 거실이 한 방이 됐다. 벽 표현이 두 가지로 잡힌 도면(3.3.1절의 `thin` 이 있는 경우)에서는 **밝은 기준(220)으로 한 번 더 이진화해 빗금을 닫힘으로 메운 뒤, 얇고 긴 것만 벽으로 받는다(`hatchedWalls`)**. 밝은 회색은 타일 격자·바닥 음영 같은 넓은 무늬에도 쓰이므로, 벽 두께의 2.5배보다 두꺼운 덩어리는 굵은 커널 열림으로 골라내 빼고, 길이가 두께의 6배에 못 미치는 조각(치수선 눈금·기호)과 이미지 가장자리에 닿은 것(테두리 띠)도 뺀다. 이 통로는 잇기를 먼저 한 뒤 길이를 본다 — 잇기 전에는 다 짧은 조각이다.

### 3.5 작은 조각 제거

4-연결 성분 분석으로 면적이 `벽두께² × 4` 미만인 덩어리를 버린다. 열림을 통과한 굵은 글자 획이나 점 기호가 여기서 걸린다.

### 3.6 경계 추적 → 다각형

마스크 테두리를 따라 걸어 닫힌 고리를 만든다. 픽셀 격자의 **꼭짓점**을 지나는 경로를 쓴다(픽셀 중심이 아니다). 그래서 좌표가 정수이고 벽 두께가 정확히 보존된다.

핵심은 **진행 방향의 오른쪽에 벽이 오도록 걷는 것**이다. 그러면 바깥 테두리는 화면 좌표(y 아래) 기준 시계 방향, 구멍은 반시계 방향이 되어 부호 있는 면적(shoelace)의 부호만으로 둘을 구분할 수 있다. 별도 판정이 필요 없다.

갈림길에서는 **오른쪽 꺾기를 우선**한다. 모서리로만 닿은 두 덩어리를 따로 뽑기 위한 것이다. 이렇게 하지 않으면 대각선으로 닿은 벽 두 개가 한 다각형으로 묶여 압출 결과가 이상해진다.

그다음 Ramer–Douglas–Peucker로 단순화한다(허용 오차 1.5px). 픽셀 경계는 계단 모양이라 그대로 두면 정점이 수천 개가 된다. 단순화 후 사각형 벽은 정점 4개가 된다.

마지막으로 구멍을 자신을 감싸는 **가장 작은** 바깥 테두리에 배정한다. 중첩된 구멍이 있어도 맞게 들어간다.

### 3.7 압출

각 다각형을 Three.js `Shape`(구멍은 `Path`)로 만들고 `ExtrudeGeometry`로 높이만큼 끌어올린다. Rhino의 `ExtrudeCrv`와 같은 동작이다.

**벽이 끊긴 자리가 그대로 문·창이 된다.** 개구부를 따로 인식해 구멍을 뚫는 처리가 없다. 열림 단계에서 문 호와 창 선이 지워졌기 때문에, 원래 벽이 없던 자리는 마스크에서도 비어 있다.

## 4. 좌표계와 3D 변환

세 좌표계를 쓴다. 섞이면 디버깅이 어려우니 처음에 정하고 주석에 적어 두는 게 좋다.

| 좌표계 | 축 | 단위 | 쓰는 곳 |
|---|---|---|---|
| 도면 픽셀 | x 오른쪽, y 아래 | px | 마스크, 다각형, 편집 입력 |
| 월드 | x 오른쪽, y 위, z 아래쪽(=도면 y) | m | Three.js 씬 |
| 정규화 | 0~1 | 없음 | LLM 주고받기 |

변환은 `s = 1 / pxPerMeter` 하나다. 도면 픽셀 `(x, y)` → 월드 `(x*s, 높이, y*s)`.

`Shape`는 XY 평면에 놓이고 압출은 +Z로 간다. 도면을 바닥에 눕히려면 이렇게 한다.

```ts
const geo = new THREE.ExtrudeGeometry(shape, { depth: height, bevelEnabled: false });
geo.rotateX(Math.PI / 2);   // XY 평면을 XZ(바닥)로 눕힌다
geo.translate(0, height, 0); // 압출이 -Y 로 갔으므로 올린다
```

이 회전 때문에 면의 법선이 뒤집힌다. 벽은 닫힌 입체라 안 보이지만, **바닥에 깔는 평면 조각은 위에서 보이지 않게 된다.** 6.1절을 보라.

### 4.1 카메라 맞추기

모델을 감싸는 구가 시야에 들어오는 거리를 계산한다. 세로·가로 시야각 중 **좁은 쪽**을 써야 좁고 긴 패널에서도 잘리지 않는다.

```ts
const vFov = (camera.fov * Math.PI) / 180;
const hFov = 2 * Math.atan(Math.tan(vFov / 2) * camera.aspect);
const dist = radius / Math.sin(Math.min(vFov, hFov) / 2);
```

반지름은 **이미지 크기가 아니라 벽이 있는 범위**로 잡는다. 도면 이미지에는 여백이 넓게 남아 있어서, 이미지 크기로 맞추면 모델이 화면 가운데 작게 박힌다.

## 5. 편집 (벽 추가·제거)

### 5.1 마우스 → 도면 좌표

`Raycaster`로 바닥 평면(`y = 0`)에 광선을 쏘고 교점의 x·z를 픽셀로 되돌린다.

```ts
const ndc = new THREE.Vector2(
  ((e.clientX - rect.left) / rect.width) * 2 - 1,
  -((e.clientY - rect.top) / rect.height) * 2 + 1,
);
raycaster.setFromCamera(ndc, camera);
raycaster.ray.intersectPlane(plane, hit);
return [hit.x / s, hit.z / s];
```

### 5.2 OrbitControls와 충돌 피하기

편집 모드에서는 왼쪽 드래그를 편집에 쓰고, 회전은 끈다. 오른쪽 드래그(이동)와 휠(확대)은 남겨 둔다.

```ts
controls.mouseButtons.LEFT = editing ? null : THREE.MOUSE.ROTATE;
controls.touches.ONE = editing ? null : THREE.TOUCH.ROTATE;
canvas.style.cursor = editing ? 'crosshair' : '';
```

`setPointerCapture`를 쓰면 캔버스 밖으로 드래그가 나가도 끊기지 않는다.

편집 모드로 들어갈 때 **위에서 보기로 자동 전환**하는 게 좋다. 기울어진 시점에서 바닥 평면에 광선을 쏘면 커서와 실제 좌표가 어긋나 보인다. 단, 모드를 바꿀 때마다 시점을 되돌리면 방해가 되므로 "보기 → 편집"으로 처음 들어갈 때만 한다.

### 5.3 벽 추가

드래그 시작점과 끝점 사이에 두께 있는 사각형을 칠한다.

- **축 스냅.** 기울기가 8° 안이면 수평·수직으로 붙인다. 대부분의 벽은 축에 평행하다.
- **길이 입력.** 길이(m)를 미리 적어 두면 드래그로 방향만 정하고 길이는 입력값을 쓴다. 치수를 알고 그릴 때 이게 있어야 쓸 만해진다.
- **끝 늘리기.** 양 끝을 두께의 절반만큼 늘린다. 이렇게 하면 T자·십자 교차에서 모서리가 맞물리고 빈틈이 생기지 않는다.
- **미리보기.** 드래그 중 반투명 다각형을 띄우고 길이를 m로 표시한다.

### 5.4 벽 제거

두 방식을 둔다.

**클릭 — 한 구간.** 클릭한 자리의 벽이 어느 방향으로 긴지 보고(가로·세로 런 길이 비교) 그 방향으로 걸어가며, 두께가 `벽두께 × 1.6`을 넘는 지점에서 멈춘다. 그 지점이 교차점이다. 결과는 "교차점 사이 벽 한 구간"이고, 이게 사람이 기대하는 단위다.

클릭 지점 자체의 두께가 이미 한도를 넘으면(교차점 한가운데) `null`을 돌려준다. 교차점 클릭으로 벽 두 개가 동시에 지워지는 것보다 아무 일도 안 하는 게 낫다.

**드래그 — 사각형.** 사각형 안을 전부 비운다. 가구 덩어리처럼 구조가 복잡한 곳을 치울 때 쓴다.

두 방식 모두 되돌리기 스냅샷을 먼저 쌓는다. `Ctrl/⌘+Z`도 받는다.

### 5.5 문 그리기

문은 벽에 난 폭이 정해진 구멍이다. 벽 지우기와 같은 연산이지만 세 가지가 다르다.

- **벽이 이어지는 방향으로만 폭을 준다.** 클릭한 자리의 벽 한 구간을 찾아(5.4절과 같은 함수) 긴 쪽을 문 폭 방향으로, 짧은 쪽(벽 두께)은 전부 관통한다. 사용자가 방향을 맞출 필요가 없다.
- **폭을 입력받는다.** 기본 0.9m(외여닫이문 유효폭)를 두고, 벽을 따라 끌면 끈 만큼이 폭이 된다.
- **벽 구간을 넘지 않게 당긴다.** 벽 끝에서 클릭해도 문이 벽 밖으로 삐져나가지 않는다.

벽이 아닌 곳에서 시작하면 아무 일도 하지 않고 그렇게 알린다. 벽을 찾는 함수가 교차점 한가운데에서 `null`을 주므로, 교차점에 문을 내려는 시도도 자연히 걸러진다.

**3D에서는 문 위에 인방(lintel)을 남긴다.** 이게 없으면 문이 벽이 그냥 끊긴 자리와 똑같이 보인다. 문 높이 2.1m 위부터 벽 높이까지를 벽과 같은 재질로 세우면 문으로 읽힌다. 벽이 문보다 낮으면 인방을 만들지 않는다.

주의할 점은 **위에서 내려다보면 인방이 문을 덮어 벽처럼 보인다**는 것이다. 이건 기하학적으로 맞지만 평면에서 문을 알아보기 어렵다. 창문은 유리를 반투명하게 깔아 위에서도 구별되는 반면 문은 그렇지 않다. 평면에서도 문을 드러내야 하면 인방 재질을 벽과 조금 다르게 하거나 바닥에 문턱 선을 그리면 된다.

## 6. 방 면적과 축척

### 6.1 건물 윤곽 판정 — 모폴로지 닫힘을 쓰지 말 것

"바깥"을 찾아야 한다. 이미지 가장자리에서 시작한 flood fill은 창문 틈으로 새어 들어와 건물 안까지 바깥으로 칠한다.

처음에는 모폴로지 닫힘(팽창 → 침식)으로 틈을 메운 뒤 flood fill을 했다. **두 가지가 깨진다.**

1. 외벽과 이미지 가장자리 사이 여백이 좁은 도면에서, 그 여백이 "메워져" 건물 안으로 잡힌다.
2. 침식이 이미지 경계 밖을 0으로 보기 때문에 가장자리 근처 외벽이 깎이고, 그 구멍으로 큰 방이 바깥으로 새어 나간다.

**걸음 예산 BFS로 바꿨다.** 이미지 밖을 끝없는 빈 공간으로 본다.

1. 모든 픽셀에서 가장 가까운 벽까지의 체비쇼프 거리를 8-연결 BFS로 구한다.
2. 벽에서 `r` 이상 떨어진 채 가장자리에서 이어지는 영역이 "먼 바깥"이다. 여기끼리는 걸음을 쓰지 않고 이어진다.
3. 먼 바깥에서 벽을 뚫지 않고 `r` 걸음까지 다가간 곳까지가 바깥이다. 남은 걸음이 많은 픽셀부터 퍼뜨린다(버킷 큐).

`r`은 개구부 최대 폭의 절반(기본 1.5m)이다. 폭이 `2r`보다 좁은 창·문 틈으로는 걸음이 모자라 들어오지 못한다. 가장자리 픽셀에는 벽까지의 거리만큼 걸음을 주어, 여백이 좁아도 벽이 깎이지 않는다.

### 6.2 방 나누기 — 개구부 후보를 막는다

처음에는 건물 안에서 벽을 **문 폭만큼**(1.3m) 모폴로지 닫힘으로 두껍게 해 방 사이 출입구를 막았다. 실제 도면 두 장을 넣어 보니 이 방식이 구획 오류의 주원인이었다 (`docs/plan-ai-roadmap.md` 2절). 결함이 셋이다.

1. 1.3m 보다 좁은 공간(복도·욕실·현관·발코니)이 통째로 사라진다. 아파트 도면에서 바닥의 24% 가 어느 방에도 들어가지 않았다.
2. 모서리 문(벽 끝이 직각 벽과 만나는 자리의 문)은 사각 커널 닫힘으로 메워지지 않는다. 두 벽의 팽창은 겹치지만 그 안에 커널 크기의 정사각형이 통째로 들어가지 않아 침식이 도로 지운다.
3. 1.3m 보다 넓은 개구부(양여닫이, 트인 거실·주방)는 막지 못한다.

지금은 **개구부 후보(6.4절)를 선분으로 임시로 막고**, 전역 닫힘은 벽의 잔 끊김을 메우는 0.4m 로만 건다. `findRooms(mask, w, h, pxPerMeter, { barriers })` 의 `barriers` 가 그 선분이다. 선분은 방 계산용 임시 마스크에만 칠하고 벽 마스크와 3D 는 건드리지 않는다. 면적도 원래 마스크 기준이다. 어떤 후보를 막을지는 판정에 따른다 — 문·창이면 막고, 트인 곳·개구부 아님이면 막지 않는다. 판정 전에는 문 폭(1.3m) 이하의 후보만 막는다.

실제 도면에서 (후보를 전부 막았을 때) 아파트는 방 4개·미배정 24.5% → 8개·8.9%, 주택은 10개·8.5% → 16개·3.7% 가 됐다.

벽이 하나도 없는 마스크는 인식 실패로 보고 빈 결과를 돌려준다. 그러지 않으면 바깥이 생기지 않아 이미지 전체가 방 하나가 되어, 추출 실패가 그럴듯한 면적으로 둔갑한다.

면적을 잴 때 주의할 점이 있다. 방 영역을 구할 때 벽 표면에 붙은 얇은 띠(3px)를 빼야 인접한 두 방이 벽 한 겹을 타고 이어지는 것을 막을 수 있다. 그런데 그 상태로 픽셀을 세면 면적이 작게 나온다. **띠를 다시 넓힌 뒤(벽·바깥은 제외) 그 픽셀 수를 면적으로 쓴다.**

1.3m보다 넓은 개구부는 열린 공간으로 본다. 거실·주방처럼 트인 곳이 한 구역으로 묶이는데, 이건 대체로 맞는 동작이다. 나누고 싶으면 사용자가 벽을 그어 닫으면 된다.

### 6.3 축척

**축척은 이 기능에서 정확도 값이 가장 큰 항목이다.** 면적은 축척의 제곱으로 움직이고, 소방 계산(보행거리·수평거리·면적당 감지기 수)은 전부 축척 위에 얹힌다.

네 경로를 둔다.

1. **가정.** 벽 두께를 0.2m로 본다. 아무 정보가 없을 때의 출발점이다. 실제와 30~50% 차이 날 수 있으니 UI에 "가정"이라고 표시해야 한다.
2. **치수선 읽기.** 도면에 적힌 치수 숫자를 읽어 확정한다. 8.8절. **치수선이 있으면 이게 답이다.**
3. **표준 치수 어림.** 치수선이 없는 도면(분양 홍보용, 숙박 소개용)은 문 폭·침대·변기 같은 표준 치수로 어림한다. 8.9절.
4. **사용자 지정.** 길이를 아는 벽이나 치수선을 따라 선을 긋고 실제 길이(m)를 입력한다. `pxPerMeter = 그은 길이(px) / 입력 길이(m)`.

1번은 2·3번이 모두 실패했을 때만 남는 출발점이다. 벽을 얼마나 두껍게 그리는지는 도면의 화풍이라 실제 두께와 상관이 약하다. 선으로 그린 주택 평면도에서 벽 6px를 0.2m로 보면 30px/m이 나오는데, 실제는 59px/m이었다. **길이로 2배, 면적으로 4배 틀린다.**

가정 경로에는 함정이 있다. **두께를 추정하는 코드와 축척을 가정하는 코드가 같은 값을 쓰면 안 된다.** 사용자가 두께 슬라이더를 내리면 축척이 따라 내려가 도면이 조용히 커진다. 스스로 잰 굵은 벽 두께를 따로 들고 있어야 한다.

```ts
let wallPx = 8;      // 지금 열림에 쓰는 두께 (사용자가 바꿀 수 있다)
let autoWallPx = 8;  // 이미지에서 스스로 잰 굵은 벽 두께. 축척 가정은 항상 이 값으로
if (!scaleFixed) pxPerMeter = autoWallPx / ASSUMED_WALL_M;
```

축척이 바뀌면 월드 크기가 전부 바뀌므로 모델을 다시 놓아야 한다(`setModel` 재호출). 마스크는 그대로다.

면적은 `픽셀 수 / pxPerMeter²`다. 한국 대상이면 평(3.3058㎡)도 함께 보여 준다.

### 6.3.1 잰 면적을 다른 입력으로 넘길 때

도면 면적을 법령 판단용 조건(영업장 바닥면적 등)으로 넘기는 순간, 계산값이 사용자가 확인한 값으로 둔갑할 위험이 생긴다. 면적은 축척의 제곱으로 움직이므로 틀린 값이 그대로 설치 대상 판정에 들어간다. 문을 세 개 둔다.

1. **저절로 넘기지 않는다.** 사용자가 버튼을 눌러 상자를 열고, 값·출처·넣을 항목을 보고, 따로 확인 표시를 해야 넘어간다.
2. **축척을 사용자가 확인한 뒤에만 넘긴다.** `scaleStatus !== 'confirmed'` 면 막고 **실제 길이 맞추기**로 보낸다. 가정·표준 치수 어림·자동 인식(확인 전)은 모두 막힌다.
3. **뜻이 같은 항목에만 넘긴다.** 도면 한 장은 영업장 바닥면적이거나 같은 용도 면적 합계일 수 있지만, 건물 연면적·지하층 면적은 건축물대장에서 확인하는 다른 값이다. 넘길 수 있는 항목을 화이트리스트로 둔다.

넘긴 값에는 출처 한 줄(`도면에서 가져옴 · <구역> · 기준 길이 <근거> · 인식한 벽과 구역으로 계산`)을 함께 저장해 조건 카드에서 계속 보이게 한다. 사용자가 그 값을 직접 고치면 출처는 지운다 — 남겨 두면 다른 값에 엉뚱한 근거가 붙는다.

판단은 `frontend/src/plan/areaImport.ts` 의 순수 함수에 모아 두고 화면은 결과만 그린다. 막히는 이유를 하나씩만 돌려주어야 화면에서 다음 행동이 하나로 정해진다.

### 6.4 개구부 후보 찾기

벽이 끊긴 자리를 두 가지 방법으로 찾아 합친다.

**행·열 스캔.** 모든 행과 모든 열에서 **벽 런 → 빈 런 → 벽 런** 순서를 찾고, 빈 런이 개구부 최대 폭(2.6m) 안이면 후보로 표시한다. 그다음 연결 성분으로 묶어 상자를 만들고, 한 변이 `벽두께 × 2.2` 안으로 얇고 다른 변이 사람 폭(0.5m) 이상이며 상자를 60% 이상 채우는 것만 남긴다. 벽 사이에 낀 문·창을 잡는다.

**벽 끝점.** 벽이 그냥 끝나는 자리(자유 끝)에서 앞쪽으로 가장 가까운 다른 벽까지를 후보로 잡는다. 행마다 벽 런의 양 끝을 보고, 그 자리에서 직각 방향 런이 벽 두께 안이면(직각 벽과 만나는 교차점이 아니면) 자유 끝이다. 곧장 앞에 벽이 있고 그 거리가 최단 거리의 1.3배 안이면 곧장 앞을 고르고, 아니면 사선도 허용한다. 모서리 문과 벽 끝 문은 이 방법으로만 잡힌다 — 어느 행·열에도 벽 → 빈칸 → 벽 순서가 없기 때문이다. 마주 보는 두 끝은 같은 선분을 두 번 만들므로 하나만 남긴다. 작은 조각(치수선 눈금·기호·가구 잔해)은 양 끝이 될 수 없다.

후보는 선분(`a`, `b`)과 경계 상자, 방향(`h`·`v`·사선 `d`), 폭, 출처(`gap`·`end`)를 갖는다. **후보는 "개구부일 수 있는 자리"다.** 문인지 창인지 트인 곳인지, 아니면 개구부가 아닌지는 AI 나 사용자가 판정한다(8.3절). 행·열 스캔 후보만으로 막으면 오히려 방이 줄어든다 — 모서리 문을 못 잡아서다.

모폴로지 닫힘의 차집합(`닫힌 것 - 원래`)으로 구하려 했으나 실패했다. 안쪽 모서리가 함께 채워지고, 커널이 큰 경우 개구부 주변이 뭉개진다. 행·열 스캔이 더 정확하고 빠르다.

### 6.5 실패했을 때 무엇을 보여 줄 것인가

도면 작업은 서버·LLM·한도를 함께 쓰므로 실패가 잦다. 실패 안내는 세 가지를 같은 자리에 놓아야 한다 — **무슨 작업이** 실패했는지, **왜** 그런지, **다음에 무엇을** 할 수 있는지.

함정은 한도다. 한도는 질문과 도면 작업이 같은 계정 쿼터를 쓰므로 서버가 "오늘 질문 한도" 라고 말하면 도면을 만지던 사용자는 자기 일과 무관한 안내로 읽는다. **작업 이름은 부르는 쪽이 붙인다.** 서버 문구를 그대로 띄우지 않는다.

로그인 권유도 조심해야 한다. 익명 사용자의 계정 한도에 걸렸을 때만 로그인이 한도를 올려 준다 — IP 한도에 걸렸다면 로그인해도 그대로다. 서버가 그 둘을 다른 코드(`rate_limited_anon` · `rate_limited`)로 구분해 주어야 화면이 거짓말을 하지 않는다.

모르는 오류를 한도나 로그인 문제로 바꿔 말하지 않는다. 코드가 없으면 서버 문구를 덧붙이고 다시 시도할 길만 준다. 자동 재시도는 하지 않는다 — LLM 호출은 돈이 들고, 같은 그림을 다시 보내면 대개 같은 답이 온다.

판단은 `frontend/src/plan/failure.ts` 의 순수 함수(작업 × 오류 코드 → 문구 + 버튼 목록)에 모으고 화면은 버튼만 그린다. 이래야 "저장 실패에 직접 길이 입력을 권하지 않는다" 같은 규칙을 테스트로 고정할 수 있다.

## 7. 계정 저장 (선택)

저장할 것은 네 가지다.

| 항목 | 형식 | 크기 |
|---|---|---|
| 축소한 원본 이미지 | JPEG 품질 0.85 | 200~400KB |
| 벽 마스크 | 1비트 PNG (벽=검정) | 20~60KB |
| 축척·두께·벽 높이·이름 | DB 열 | — |
| 판정(개구부 종류·문·창·구역 이름) | JSONB (`annotations`) | 수 KB |

판정은 후보 번호가 아니라 **선분의 양 끝 좌표**로 저장한다. 후보 번호는 마스크가 바뀌면 달라진다. 불러올 때 지금 후보와 양 끝이 벽 두께 안에서 맞는 것을 같은 개구부로 본다. 서버는 JSON 객체인지와 크기(64KB)만 보고 형식은 화면이 정한다.

마스크를 PNG로 두는 게 좋다. RLE나 JSON 좌표 배열보다 작고, 브라우저가 디코딩을 해 주고, 디버깅할 때 눈으로 볼 수 있다. 저장 시 마스크 1 → 검정(0), 0 → 흰색(255). 불러올 때 밝기 128 미만을 1로 읽는다.

API 계약은 이렇다. 프레임워크와 무관하다.

```
GET    /api/plans          → 목록
POST   /api/plans          → 저장 (multipart: 메타 필드 + image + mask)
GET    /api/plans/:id      → 메타 + 파일 주소(서명, 1시간)
PUT    /api/plans/:id      → 덮어쓰기
DELETE /api/plans/:id
```

파일은 비공개 저장소에 두고 소유자만 읽게 한다. 우리는 Supabase Storage의 비공개 버킷에 `{userId}/{planId}/image.jpg`로 두고, 조회할 때 1시간 서명 URL을 발급한다. S3면 presigned URL, 자체 서버면 인증된 스트리밍 엔드포인트다.

이 프로젝트는 비로그인 사용자도 익명 세션을 갖고, 나중에 소셜 로그인하면 익명 계정에 연결된다. 그래서 비회원도 저장할 수 있고 로그인 후에도 남는다. 이런 구조가 없으면 저장 버튼을 누를 때 로그인을 요구해야 한다.

## 8. LLM 보완 (선택)

### 8.1 역할 분담이 전부다

시각 LLM은 **픽셀 단위 기하에 약하다.** "벽 좌표를 다시 그려 달라"고 하면 결과가 호출마다 흔들리고 검증할 방법이 없다. 반대로 "이 결과가 맞는지 보고 무엇을 고칠지 말해 달라"는 잘한다.

그래서 이렇게 나눈다.

```
알고리즘이 그린다 → LLM이 검토·판정한다 → 알고리즘이 고친다 → 사용자가 고른다
```

LLM은 좌표를 만들지 않고 **우리가 매긴 번호나 격자 칸을 되돌려 받는다.** 수정은 기존 편집 함수(`fillRect`, `paintWall`)가 한다. 그래서 LLM이 틀려도 되돌리기가 되고, 결과가 항상 마스크 편집 연산으로 표현된다.

### 8.2 무엇을 보내는가

원본 위에 네 겹을 올린 JPEG 한 장을 보낸다(폭 1024px, 품질 0.85).

1. 검출된 벽 — 빨간 반투명
2. 격자 — 12열 × 비율에 맞춘 행, 칸 이름 `A1`~`L8`
3. 개구부 후보 — 파란 선분과 번호 (사선 후보도 제 자리에 보이도록 사각형이 아니라 선분으로 그린다)
4. 구역 — 초록 원과 번호

같은 내용을 글로도 보낸다. 격자 크기, 지금 매개변수(어두움 기준·벽 두께·1m당 픽셀), 개구부 후보 목록(번호·칸·폭·**양쪽 구역 번호**), 구역 목록(번호·칸·면적).

양쪽 구역 번호는 후보 선분 가운데에서 직각 방향으로 벽 두께 두 배만큼 떨어진 두 점이 어느 구역인지 본 것이다. "구역 2↔3 사이"면 문일 가능성이, "구역 1↔1"이면 지금 나뉘지 않은 트인 곳일 가능성이 높다. 그림만 보는 것보다 이런 관계 정보를 글로 주는 쪽이 정확하다는 결과가 있다(Floorplan2Guide).

격자를 그림에 직접 그려 넣는 것이 중요하다. "왼쪽 위 방"처럼 말로 받으면 어디인지 특정할 수 없다. `D6` 칸이면 픽셀 사각형으로 바로 환산된다.

### 8.3 무엇을 받는가

구조화 출력(`json_schema`, `strict`)으로 받는다. 일곱 항목이다.

| 항목 | 내용 | 적용 방법 |
|---|---|---|
| `quality` | 0~1 점수 | 재시도 판단 |
| `summary` | 한두 문장 총평 | 표시 |
| `falseWalls` | 벽이 아닌데 잡힌 칸 + 무엇인지 | 칸 안에서 **주 벽 네트워크(가장 큰 덩어리)에 붙지 않은 픽셀만** 지운다. 가구·글자는 대개 따로 떨어진 덩어리라 지워지고, 같은 칸의 진짜 벽은 남는다. 벽에 붙은 가구는 안 지워지는 쪽으로 틀린다 |
| `missingWalls` | 빠진 벽의 양 끝 (0~1 정규화) | 스냅 후 `paintWall`. 선분 ±3px 에 원본의 어두운 선이 60% 이상 보여야 기본으로 고른다. 아니면 "확인이 필요합니다" 를 붙여 기본 해제 |
| `openings` | 후보 번호별 `door`/`window`/`open`/`not_opening` | 문·창이면 그 후보를 막아 방을 나누고(6.2절) 3D 에 인방·창턱을 세운다. 트인 곳·개구부 아님이면 막지 않는다 |
| `rooms` | 번호별 이름 | 구역 표시에 반영 |
| `scale` | 1m당 픽셀 + 근거 | `pxPerMeter` 교체 |
| `params` | 권하는 어두움 기준·벽 두께 | 재분석 |

빠진 벽만 좌표로 받는다. 격자 칸으로는 선을 표현할 수 없기 때문이다. 대신 적용할 때 양 끝을 **반경 `벽두께 × 2` 안의 가장 가까운 벽 픽셀에 스냅**하고 축 스냅을 건다. LLM 좌표가 몇 픽셀 어긋나도 기존 벽에 붙는다. 시각 모델은 없는 벽을 지어내기도 한다(없는 대상 거부율이 거의 0 인 벤치마크가 있다). 그래서 스냅한 선분을 따라 원본에 어두운 선이 실제로 있는지 본다 — 증거가 모자라면 제안은 남기되 기본 해제다.

응답 검증은 두 겹으로 한다. 모델이 스키마를 지켜도 내용이 엉뚱할 수 있다.

- 스키마 검증(zod 등)으로 형식과 범위를 다시 확인한다.
- **우리가 보낸 번호만 받아들인다.** 개구부·구역 번호를 집합으로 두고 필터링한다. 모델이 없는 9번, 7번을 만들어 보내는 일이 실제로 있었다.

두 번째 검증은 **너그럽게** 해야 한다. 검토는 참고용 제안이므로, 총평이 400자를 넘었다는 이유로 호출 전체를 버리면 안 된다. 글은 자르고, 수는 범위 안으로 당기고, 목록이 한도를 넘으면 잘라내고, 목록 안의 한 항목이 깨지면 그 목록만 비운다.

다만 **모델이 그림을 실제로 봤다는 증거가 되는 항목은 필수로 둔다.** 우리는 점수와 총평 두 개다. 전부 너그럽게 하면 모델이 빈 객체를 보내도 "품질 100점, 제안 없음"으로 통과해 실패가 가려진다.

검증이 실패했을 때는 어긋난 경로와 사유를 로그에 남긴다. 그러지 않으면 간헐적 실패의 원인을 찾을 수 없다.

`strict` 모드는 모든 객체에 `additionalProperties: false`와 모든 속성이 `required`일 것을 요구한다. 선택 항목은 `type: ['number', 'null']`로 표현한다. 이 조건을 시험으로 지키게 하는 게 좋다(스키마를 재귀로 순회해 확인).

### 8.4 매개변수 제안은 자동으로 적용하지 않는다

처음에는 품질이 0.6 미만이고 매개변수 제안이 있으면 그 값으로 다시 추출해 한 번 더 검토했다(최대 2회). 없앴다. 두 가지가 나빴다. AI 가 두께를 지정하면 빗금 채움·두 봉우리 추정을 건너뛰어 빗금 도면에서 돈을 쓰고 더 나빠질 수 있었고, 재추출이 사용자의 편집과 되돌리기를 지웠다. 지금은 제안을 체크 목록의 한 항목("권고 매개변수로 다시 추출 — 편집과 판정이 지워집니다", 기본 해제)으로 보여 주고 사용자가 고른다.

### 8.5 언제 돌리는가

**검토는 자동으로, 적용은 수동으로** 나누는 게 좋다. 사용자가 도면을 올리면 검토 버튼을 따로 누르게 하지 말고 한 번 자동으로 돌린다. 단 **벽을 먼저 화면에 띄우고 검토는 그다음에** 돌린다. 추출은 1초 안에 끝나는데 검토는 10초 넘게 걸리므로, 검토를 기다리며 빈 화면을 보여 줄 이유가 없다.

자동으로 돌리지 말아야 할 경우가 있다.

- **샘플·기본 도면의 자동 적재.** 페이지를 열 때마다 유료 호출과 하루 한도가 소모된다. 결과도 매번 같다. 사용자가 버튼을 눌렀을 때만 돌린다.
- **저장본 불러오기.** 이미 검토를 거친 도면이다.

자동 검토를 넣으면 경쟁 상태가 생긴다. 검토하는 10초 사이에 사용자가 다른 도면을 올리거나 같은 도면의 벽을 고칠 수 있고, 그러면 늦게 도착한 제안이 바뀐 도면에 적용된다. 두 겹으로 막는다. **도면 세대 번호**는 도면을 새로 올릴 때 올라가고, **revision** 은 벽·축척·판정이 바뀔 때마다 올라간다. 호출 전에 둘을 잡아 두었다가 응답을 받은 뒤 비교해 바뀌었으면 결과를 버리고, 제안을 적용하는 시점에 다시 비교한다(검토 결과를 띄워 둔 채 벽을 지우고 나서 적용을 누르는 경우).

같은 이유로 마스크를 다시 추출할 때(도면 교체, 두께 슬라이더 조작) 지난 제안을 지우고 방 목록도 비워야 한다. 방 목록을 비우지 않으면 뒤따르는 검토가 이전 도면의 구역 번호를 그대로 보내게 된다. 방 계산이 디바운스되어 있다면 특히 그렇다.

검토 중에는 버튼을 잠가 중복 호출을 막고, 끝나면 반드시 되살려 다시 눌러 볼 수 있게 한다.

### 8.6 적용은 사용자가 고른다

제안을 체크 목록으로 보여 주고 고른 것만 적용한다. 자동 적용하지 말 것. 실제 결과를 보면 계단실 벽을 개구부로 오해해 "벽을 추가하라"고 하는 오판이 섞인다. 78점짜리 검토에서 제안 20건 중 3건이 오판이었다.

적용은 되돌리기 스냅샷에 넣어 한 번에 취소할 수 있게 한다. 스냅샷에는 마스크만이 아니라 **문·창·구역 이름·개구부 판정·축척**을 함께 담는다. 벽만 되돌리면 판정·축척과 어긋나 방이 갑자기 바뀐다.

### 8.7 모델 선택

**OpenRouter의 Gemini 계열을 권한다.** 이 프로젝트는 `google/gemini-3.8-flash`를 기본으로 두고 환경변수(`OPENROUTER_VISION_MODEL`)로 바꿀 수 있게 했다.

이유는 이렇다.

- 도면·문서 같은 공간 정보 읽기에 강하다. 한국어 도면 글자("KITCHEN", "화장실")를 읽어 구역 이름을 붙이는 것도 잘한다.
- 컨텍스트가 100만 토큰이라 이미지를 여러 장 보내도 여유가 있다.
- 단가가 낮아 검토를 2~3회 반복해도 호출당 1센트 미만이다.
- OpenRouter를 쓰면 모델 ID 한 줄로 후보를 바꿔 비교할 수 있다. GPT 계열도 같은 경로로 부를 수 있어, 제공자 직접 호출은 전용 기능이 필요할 때만 의미가 있다.

주의할 점. OpenRouter에서 `provider.require_parameters: true`를 켜면 OpenAI 계열은 조건을 만족하는 엔드포인트가 없어 전면 차단된다. 모델 목록의 `supported_parameters`를 그대로 믿지 말고 실제로 호출해 확인해야 한다. 이 프로젝트는 그 경험 때문에 "검증을 통과한 모델만 허용 목록에 넣는다"를 규칙으로 두었다.

비용은 기록하고 하루 예산에 합산하는 게 좋다. 우리는 호출마다 모델·토큰·비용·품질·오류를 표에 남기고, 기존 답변 비용과 합쳐 하루 상한을 검사한다.

실측(기본 사무실 도면, 1024px 그림): 11초, 입력 약 1천 토큰 + 이미지 1장, 품질 78점.

### 8.8 치수선으로 축척 확정하기

검토와 별개로 도는 두 번째 호출이다. 역할 분담은 같다. **모델은 숫자를 읽고, 축척 계산과 검증은 알고리즘이 한다.**

**무엇을 보내는가.** 겹쳐 그린 것이 하나도 없는 원본이다. 폭 1600px(검토용 1024px보다 크게) — 치수 글자가 작아 격자나 빨간 벽이 얹히면 못 읽는다.

**무엇을 받는가.** 치수 숫자마다 세 가지다.

| 항목 | 내용 |
|---|---|
| `mm` | 숫자를 mm로 고친 값 |
| `from`, `to` | 그 숫자가 **재고 있는 구간**의 양 끝 (0~1 정규화) |
| `label` | 도면에 적힌 글자 그대로 |

프롬프트에서 "숫자 자체의 위치가 아니라 구간을 끊는 두 표시(사선·화살표·치수보조선)의 위치"라고 못 박아야 한다. 그러지 않으면 글자 상자의 좌표가 온다.

**계산은 두 단계다.**

1. **구간마다 따로 재서 이상한 것을 버린다.** `px/m = 구간 길이(px) / (mm/1000)`. 중앙값에서 12% 넘게 벗어난 구간은 숫자를 잘못 읽은 것으로 본다. 실제로 3,670을 367로, 2,620을 2,920으로 읽는 일이 있었다.
2. **남은 구간을 치수 사슬로 묶어 다시 잰다.** 같은 치수선 위에 있고 앞 구간 끝에 이어지는 것들을 하나로 묶어, `사슬 전체 길이 / 사슬 전체 치수`로 계산한다.

2단계가 없으면 정확도가 모자란다. **모델이 집어 주는 구간 끝은 몇 픽셀씩 어긋난다.** 실제 아파트 도면에서 구간 하나씩 보면 88.4 ~ 100.3 px/m로 흩어졌고, 중앙값은 참값보다 2.7% 낮았다(면적으로 5.3%). 사슬로 묶으면 중간 끝점의 오차는 서로 지워지고 바깥 두 끝의 오차만 긴 길이에 나뉘어 들어간다.

같은 도면에서 결과를 대조했다.

| 방법 | px/m | 참값 대비 | 바닥 면적 |
|---|---|---|---|
| 벽 두께 0.2m 가정 | 135 | +46% | 41.6㎡ |
| 구간별 중앙값 | 89.5 | −2.8% | 94.5㎡ |
| **치수 사슬** | **92.19** | **+0.1%** | **89.2㎡** |

참값 92.1 px/m은 치수선 픽셀을 직접 재서 구했다(연한 선이라 이진화 기준을 235로 올려야 보인다). 위 치수선이 1,520+1,365+3,045+2,920 = 8,850mm를 815px에 담고 있었다.

**못 믿겠으면 null을 돌려준다.** 틀린 축척은 축척이 없는 것보다 나쁘다. 조건은 이렇다.

- 쓸 만한 구간이 2개 미만이면 버린다 (200mm 미만, 24px 미만 구간은 애초에 세지 않는다).
- 구간이 둘뿐이면 서로 4% 안으로 맞을 때만 받아들인다. 서로 맞는지가 유일한 검증이기 때문이다.

**언제 돌리는가.** 도면을 올릴 때 자동으로, **검토보다 먼저** 돈다. 검토가 면적과 개구부 폭을 보고 판단하므로 축척이 먼저 맞아야 한다. 검토와 같은 세대 번호 검사를 걸어 늦게 온 결과를 버린다. 축척이 확정되면 검토가 내놓는 축척 제안은 기본으로 꺼 둔다.

실패해도 조용히 넘어간다. 축척 가정이 그대로 남고 사용자는 축척 모드로 직접 맞출 수 있다.

### 8.9 치수선이 없는 도면 — 표준 치수 어림

같은 호출에서 함께 받는다. 치수선을 하나도 못 찾았을 때만 쓴다.

모델에게 "1m당 몇 픽셀인지"를 바로 묻지 않는다. **무엇을 쟀는지(`what`), 그것의 표준 치수(`meters`), 그림에서 차지하는 픽셀(`px`)** 세 가지를 물건마다 받는다. 나누는 것은 우리가 한다. 그래야 근거가 눈에 보이고, 말이 안 되는 항목을 걸러낼 수 있다.

**서로 다른 물건으로 셋 이상을 요구하는 것이 핵심이다.** 하나만 받으면 호출마다 결과가 흔들린다. 실제로 값 하나만 받았을 때 같은 도면에서 50 · 53 · 57 px/m이 나왔다 — 면적으로 ±25%다. 셋 이상 받아 중앙값을 쓰면 55 · 57 · 57 · 59로 좁아진다(±3.5%). 치수 사슬(8.8절)과 같은 원리다.

프롬프트에 표준 치수 목록을 적어 준다. 실내문 0.9m, 현관문 1.0m, 변기 0.7m, 욕조 1.7m, 세면대 0.6m, 퀸 침대 1.5×2.0m, 킹 침대 1.9×2.0m, 싱크대 깊이 0.6m, 냉장고 0.9m, 계단 폭 1.0m, 식탁 의자 0.45m. **재는 방향도 함께 적어야 한다** — 침대는 세로 2.0m, 문은 열리는 폭이다.

범위 검사는 간단히 한다. 1m가 4px보다 작으면 건물이 화면을 한참 넘고, 긴 변의 절반보다 크면 건물이 2m도 안 된다는 뜻이다.

이 값은 **확정이 아니다.** 화면에 "표준 치수 N개 어림"으로 표시하고, 정확히 맞추려면 축척 모드를 쓰라고 안내한다. 그래도 벽 두께 가정보다는 훨씬 낫다. 어떤 주택 평면도에서 30px/m(가정) → 57px/m(어림)으로 바뀌었고, 참값은 59px/m이었다.

## 9. 우리가 밟은 함정

옮길 때 같은 자리에서 막힐 가능성이 높은 것들이다.

**바닥 조각이 안 보인다.** `rotateX(π/2)`로 눕히면 법선이 아래를 향하고 뒷면 제거로 사라진다. 방 바닥 색을 칠했는데 화면에 아무것도 안 나왔다. `side: THREE.DoubleSide`로 해결한다. 벽은 닫힌 입체라 이 문제가 없어서 원인을 찾기 어렵다.

**RDP가 정점을 버린다.** Ramer–Douglas–Peucker 재귀에서 분할점을 `keep` 표시하지 않으면 사각형이 삼각형이 된다. 분할점을 찾은 즉시 표시해야 한다.

**닫힌 고리의 이음매에 정점이 남는다.** RDP는 열린 선분용이다. 닫힌 고리는 가장 먼 두 점으로 갈라 두 번 돌려야 하는데, 그래도 이음매 근처에 공선점이 남는다. 마지막에 "앞뒤 점과 거의 일직선인 점"을 반복해 제거한다.

**모폴로지 닫힘이 가장자리 벽을 깎는다.** 침식이 경계 밖을 0으로 보기 때문이다. 6.1절 참고. 건물 윤곽 판정은 걸음 예산 BFS로 바꿔 피했지만, 3.3.1절에서 빗금을 메우려고 닫힘을 다시 쓰게 되면서 같은 자리를 다시 밟았다. 여백 없이 잘린 도면에서 외벽이 반지름만큼 깎이고 두께가 20px 대신 18px로 잡혔다. **닫힘 안에서 빈 테두리를 덧대고 끝나면 잘라내면 된다.** 팽창분이 들어갈 자리가 실제로 있으면 침식이 제대로 되돌린다.

```ts
export function morphClose(mask, w, h, k) {
  const pad = k;               // 빈 테두리를 덧댄다
  // … 큰 배열에 옮겨 담고 erode(dilate(…)) 한 뒤 원래 크기로 잘라낸다
}
```

**가는 선이 "얇은 벽"으로 뽑힌다.** 두께 봉우리를 둘 찾게 만들면 바로 이 함정이 생긴다. 1~3px짜리 런은 어느 도면에나 널려 있어서, 하한이 없으면 글자·가구 선이 두 번째 봉우리를 차지한다. 그러면 열림 커널이 3으로 내려가 **걸러 내는 단계가 무력화된다.** 증상이 고약하다 — 벽이 사라지는 게 아니라 가구가 벽으로 남고, 그 결과가 구역 분리에서 뒤늦게 드러난다. 4px 하한으로 막는다. 3.3.1절.

**두께 슬라이더가 축척을 같이 바꾼다.** 두께 하나가 열림 커널과 축척 가정을 겸하면, 슬라이더를 27에서 5로 내렸을 때 축척이 5.4배 틀어지고 면적이 19배가 된다. 거실이 440㎡로 나왔다. 6.3절.

**추론 토큰이 응답 예산을 먹는다.** 구조화 출력의 본문이 짧다고 `max_tokens`를 짧게 잡으면 안 된다. 치수 읽기 호출에서 2,000을 줬더니 추론에만 1,357을 쓰고 본문이 잘려 **빈 문자열**이 왔다. 오류가 아니라 빈 응답이라 원인이 안 보인다. 6,000으로 올렸다. 검토 호출도 같은 이유로 올렸다.

**카메라가 모델을 작게 보여 준다.** 이미지 크기가 아니라 벽 범위로 맞춰야 한다. 도면 여백이 넓다.

**드래그 끝점 계산이 시작점을 잃는다.** 드래그 종료 핸들러에서 `dragStart`를 먼저 `null`로 만든 뒤 끝점 계산 함수를 부르면, 그 함수가 시작점을 못 찾아 축 스냅과 길이 입력이 조용히 무시된다. 미리보기는 정상이라 발견이 늦다. 시작점을 인자로 넘기게 고쳤다.

**회색 벽을 놓친다.** 이진화 기준 110은 검정 벽만 잡는다. 160으로 올린다.

**`FormData`에 `Content-Type`을 직접 넣으면 안 된다.** 경계 문자열이 빠져 서버가 본문을 못 읽는다. JSON 요청에만 헤더를 붙이도록 분기한다.

**상태 메시지 순서.** 저장 후 목록을 다시 읽는 비동기 함수가 상태 메시지를 덮어써서, 방금 띄운 "저장했습니다"가 사라진다. 목록 갱신을 먼저 하고 메시지를 나중에 띄운다.

**응답 스키마를 너무 조이면 간헐적으로 실패한다.** 구조화 출력이 형식은 지켜 주지만 글 길이나 수의 범위는 지켜 주지 않는다. 총평이 400자를 넘어 검토 전체가 버려지는 일이 있었다. 같은 도면을 다시 검토하면 성공하니 원인을 찾기 어렵다. 8.3절의 너그러운 검증과 실패 로그가 답이다.

**자동 검토가 이전 도면의 방 목록을 보낸다.** 방 계산이 디바운스되어 있으면, 추출 직후 검토를 돌릴 때 방 목록이 아직 이전 도면 것이다. 추출할 때 방 목록을 비워 두면 검토가 새로 계산하고 지나간다.

**모드별 입력칸이 캔버스를 밀어 낸다.** 편집 모드마다 다른 입력칸을 캔버스 위에 두면, 모드를 바꿀 때 칸 높이가 달라져 캔버스가 몇 픽셀 위아래로 움직인다. 사용자에게는 모델이 살짝 튀는 정도지만, 자동 시험에서 좌표를 미리 재 두었다가 모드를 바꾸고 클릭하면 엉뚱한 곳을 찍는다. 시험은 모드를 바꾼 뒤 캔버스 좌표를 다시 재야 한다.

**Three.js를 정적으로 import하지 말 것.** 압축 후 190KB다. 도면 기능을 안 쓰는 사용자에게 내려보낼 이유가 없다. 동적 `import()`로 별 청크로 분리하면 도면 탭을 열 때만 내려간다.

**기하를 버릴 때 `dispose()`를 부를 것.** 벽 높이 슬라이더는 움직일 때마다 전체 기하를 다시 만든다. 정리하지 않으면 GPU 메모리가 계속 쌓인다.

## 10. 시험 방법

1·2층이 순수 함수라서 브라우저 없이 시험할 수 있다. 이게 이 설계의 가장 큰 실익이다.

작은 합성 마스크를 코드로 만들어 확인한다. 실제 도면 이미지는 회귀 시험에 쓰기 나쁘다. 무엇이 정답인지 적기 어렵고, 값을 조금 바꾸면 결과가 흔들린다.

```ts
// 예: 문으로 끊긴 벽은 구멍 없이 바깥 테두리 하나로 남는다
const mask = new Uint8Array(w * h);
// 사각 외곽을 두께 2로 채우고, 아래 벽 일부를 비운다
const polys = buildPolygons(traceLoops(mask, w, h), 1);
expect(polys).toHaveLength(1);
expect(polys[0].holes).toHaveLength(0);
```

이 저장소의 시험 항목은 이렇다(화면 19건 + 서버 5건). 이식할 때 같은 항목을 만드는 것을 권한다.

- 이진화: 어두운 픽셀만 1
- 두께 추정: 얇은 가구선이 섞여도 벽 두께를 맞힌다
- 열림: 얇은 선은 지우고 벽 두께는 바꾸지 않는다
- 경계 추적: 속 빈 사각형 → 바깥 1개 + 구멍 1개, 부호 있는 면적 확인
- 경계 추적: 문으로 끊긴 벽 → 구멍 없음
- 경계 추적: 모서리로만 닿은 두 덩어리 → 따로 뽑힘
- 단순화: 계단 모양 대각선 → 한 변
- 추출 전체: 합성 도면에서 벽만 남고 가구·글자·문 호는 버려진다
- 편집: `snapToAxis`가 기울어진 선은 그대로 둔다
- 편집: `paintWall` 축 스냅·두께·끝 늘리기
- 편집: `wallSegmentAt`이 교차점 사이만 찾고, 교차점 한가운데는 `null`
- 편집: `cutOpening`이 가로·세로 벽에 폭만큼 뚫고, 끌면 끈 만큼이 되고, 벽 구간을 넘지 않는다 (5건)
- 닫힘: 좁은 틈만 메운다
- 방: 문으로 이어진 두 방을 따로 재고 바깥은 세지 않는다
- 개구부: 문·창은 찾고 모서리는 무시한다
- 끊긴 벽 잇기: 같은 줄에서 좁게 끊긴 벽은 잇고, 문 폭으로 끊긴 자리와 커널보다 먼 나란한 벽은 건드리지 않는다
- LLM: 프롬프트에 격자·번호가 들어간다
- LLM: strict 스키마가 모든 속성을 `required`로 둔다
- LLM: 이미지를 data URL로 보내고, 보낸 번호만 받아들인다
- LLM: 점수·총평이 없는 응답은 오류로 분류한다
- LLM: 길이·범위를 넘긴 값은 버리지 않고 다듬는다
- 두 가지 두께: 빗금 내벽이 있는 합성 도면에서 굵은 벽과 얇은 벽을 따로 찾는다
- 두 가지 두께: 빗금 내벽은 남기고 가구는 버리며, 돌려주는 두께는 굵은 쪽이다
- 두 가지 두께: 두께를 지정하면 그 두께 하나로만 본다
- 축척: 치수 사슬 전체로 재므로 구간 끝이 어긋나도 축척은 맞는다
- 축척: 잘못 읽은 치수 하나는 중앙값이 눌러 버린다
- 축척: 서로 안 맞으면 축척을 내지 않는다. 구간이 둘뿐이면 더 엄하게 본다
- 축척: mm·cm·m 어느 단위로 적혀도 같은 값이 나온다
- 축척: 치수선이 없으면 표준 치수 여러 개의 중앙값을 쓰고, 하나를 잘못 봐도 버틴다. 물건 하나뿐이거나 서로 안 맞으면 어림하지 않는다
- 축척: 말이 안 되는 근거(1m가 2px, 표준 치수 0)는 버린다
- 가는 선: 1~2px 선이 아무리 많아도 얇은 벽으로 뽑지 않고, 가구는 마스크에 남지 않는다

실제 도면으로는 `tools/plan3d/diag-rooms.ts` 로 단계별 마스크와 방 수·미배정 면적을 찍어 본다. 브라우저 흐름(올리기 → 치수 읽기 → 검토 → 적용 → 되돌리기)은 `e2e/run-aside.sh plan` 이다.

UI와 3D는 단위 시험이 어렵다. 실제 브라우저를 띄워 드래그·클릭을 자동으로 재현하고, 상태 메시지와 스크린샷으로 확인하는 편이 빠르다. 이 프로젝트는 그 방식으로 위 함정 중 절반을 찾았다.

## 11. 이식 순서

권하는 순서다. 각 단계가 끝나면 눈으로 확인할 것이 생긴다.

1. `walls.ts`를 복사하고 단위 시험을 옮긴다. 브라우저 없이 통과하는지 본다.
2. 이미지 업로드와 마스크 추출을 붙인다. 마스크를 캔버스에 흑백으로 그려 눈으로 확인한다. **이 단계에서 파라미터 감각을 잡아야 한다.** 목표 도면 몇 장으로 어두움 기준과 두께 추정이 맞는지 본다.
3. Three.js 뷰어를 붙여 압출한다. 좌표 변환과 카메라 맞추기가 여기서 끝난다.
4. 편집(벽 추가·제거·문 그리기·되돌리기)을 붙인다. `Raycaster`와 `OrbitControls` 충돌을 해결한다.
5. `rooms.ts`·`openings.ts`와 축척 입력을 붙인다.
6. (필요하면) 저장 API를 붙인다.
7. (필요하면) LLM 을 붙인다. **치수선 읽기(8.8절)를 검토보다 먼저 붙이는 것을 권한다.** 독립적으로 쓸모가 있고, 검토가 면적을 보고 판단하므로 축척이 먼저 맞아야 한다.

1~5단계까지가 이 기능의 핵심이고, 순수 함수 복사 + 뷰어·UI 재작성이라 며칠 규모다. 6·7단계는 백엔드와 LLM 사정에 따라 달라진다.

## 12. 이 기능의 한계

옮기기 전에 알아야 할 것들이다. 알고리즘을 바꿔도 쉽게 해결되지 않는다.

- **두께로만 판단한다.** 두꺼운 가구 블록(책상 군, 계단, 엘리베이터 표시)은 벽으로 잡히고, 얇게 그린 벽은 빠진다. LLM 검토와 수동 편집으로 메운다.
- **벽 표현이 셋 이상이면 둘까지만 본다.** 3.3.1 절은 봉우리를 두 개 찾는다. 외벽·내벽·칸막이를 각각 다르게 그린 도면은 가장 얇은 것이 기준이 되어 노이즈가 늘어난다.
- **방 나누기가 축척에 민감하다.** 후보 폭의 상한(2.6m)과 판정 전 기본값(1.3m 이하만 막기)이 픽셀로 환산되므로, 축척이 틀리면 방 개수가 달라진다. **구역 분리가 이상하면 알고리즘보다 축척을 먼저 의심해야 한다.**
- **후보가 없는 자리는 못 나눈다.** 벽이 통째로 빠져 끝점조차 없으면 후보가 생기지 않는다. AI 의 빠진 벽 제안이나 사용자의 벽 그리기로 메운다.
- **판정 전에는 1.3m 보다 넓은 개구부를 막지 않는다.** 거실·주방처럼 트인 곳을 잘못 막는 것보다 낫다고 봤다. AI 검토나 사용자 판정이 오면 문·창인 것만 막는다.
- **문과 창을 자동으로 구분하지 못한다.** 마스크에서는 둘 다 "벽이 없는 자리"다. LLM 판정이나 사용자가 문 그리기로 지정해야 갈린다.
- **축척을 이미지만으로는 알 수 없다.** 치수선 글자를 읽거나 사용자가 넣어야 한다.
- **한 층만 다룬다.** 여러 층을 쌓으려면 층 목록과 높이 오프셋을 더해야 한다.
- **손그림·저품질 스캔은 잘 안 된다.** 선이 끊기고 두께가 일정하지 않다. 전처리(이진화 적응형, 기울기 보정)가 더 필요하다.
- **벽이 축에 평행하지 않으면 결과가 거칠다.** 사선 벽은 단순화 후에도 계단이 남을 수 있다. 허용 오차를 키우면 나아지지만 직각 벽이 뭉개진다.
