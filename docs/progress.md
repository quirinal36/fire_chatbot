## 2. 구현된 것

### 수집 (M2)

- 법령 6종, NFPC·NFTC 20종, 소방청 해석 2건. 29개 버전(시행예정 1개 포함), 조항 단위 5,543개
- target별 어댑터와 계약 테스트. 법령 API의 형태 불일치 7종을 흡수한다:
  - 항·호 단일 객체
  - 줄 배열 본문
  - 6자리 별표번호
  - resultCode 없음
  - 빈 문자열 부칙
  - 붙어 있는 소수점 절 번호
  - `<img>` 표
- 조·항·호·목, 별표 번호 계층, 부칙, 해석 locator. 괘선 표·이미지·빈 이유는 `needs_review`로 두고 규칙 근거에서 뺀다
- 버전 보존(현행·시행예정·연혁), 원자적 저장, 재실행 멱등성, 파서 버전별 재정규화
- 원문 JSON·별표 PDF/HWP는 Storage에 보관하고, 인증값(OC)은 저장하지 않는다

### 검색 (M3)

- 정확 일치 + 키워드(pg_trgm) + 벡터(OpenAI) → RRF. 코드·법령명·설치 대상 질문 범위 검색
- 게시 상태·기준일·공개 범위·임베딩 revision을 DB 함수에서 강제
- Recall@10 **0.95** (65건, 정답 초안)
- 근거 카드 `GET /api/sources/:id`: 버전 고정, 현행 링크, 별표 원본

### 챗봇 (M4)

- `POST /api/chat` SSE. 요청 번호로 중복을 막는다(재생·처리 중·재시도)
- 비회원 익명 세션, 사용자·IP·일일 비용 한도
- 구조화 출력 검증: 인용 id, 근거에 없는 조항, URL, 규칙 없는 단정, 규칙과 다른 결론
- 1회 재요청 후 근거 목록 fallback. 근거가 부족하면 모델을 부르지 않는다
- 답변 실행 기록: 모델·프롬프트·규칙·corpus 버전, 근거, 입력, 토큰·비용·지연
- 화면: 진행 상태, 인용 칩, 근거 카드, 추가 질문, 오류 신고, 대화 복원

### 규칙 (M5)

- 선언형 규칙 실행기(삼값 논리, eval 없음). 학원 규칙 12종, 판단표 사례 38건 통과
- 영업장 사례 API: 필드 상태 3종, 질문에서 후보 추출, revision 충돌 감지, 판단 캐시
- 규칙 근거는 게시·현행·파싱 확인 단위만 허용(DB 트리거). 운영은 승인 규칙만 실행한다
- 화면: 내 영업장 탭(조건 입력·확인·판정 표·근거)

### 관리자·운영 (M6)

- 관리자 화면·API:
  - 문서 버전 게시·반려·비교
  - 규칙 승인·게시·재검토
  - 자료 공개·전송 승인
  - 답변 추적, 신고 처리, 수집 작업, 내부 자료 등록, 운영 지표
- 개정 감지 → 영향 규칙 무효 → 추가 확인으로 전환 → 재승인 후 판단 재개
- lease 기반 작업 큐, Vercel Cron 매일 03:00 KST

### 검증 (M7)

- 보안 교차 검증 운영 67/67, 장애 주입, 동시 요청 한도
- 부하 100건: 질문당 $0.0073, p95 12.4초, 인용 조회 불가 0
- 테스트: 서버 단위·계약·규칙 146건, 프런트 14건, DB 검증 SQL 4종, 브라우저 흐름 4종(Aside 브라우저, `./e2e/run-aside.sh`)

### 운영 준비 (M8 일부)

- 운영 인수인계·이용 안내·결정 기록·검수 체크리스트
- 백업·복원 검증: 17개 테이블과 원문 133개 일치
- 운영 롤백·복귀 시험 완료, Preview·운영 비밀값 분리(진단·Cron)

## 5. 알려진 한계

- 조건을 빠뜨린 요약처럼 의미 수준의 답변 오류는 형식 검증으로 다 막지 못한다. 담당자 검수와 오류 신고로 보완한다
- 좁은 화면에서 대화 목록을 열 수 없다
- DB가 뭄바이 리전이라 질문당 약 1초가 더 걸린다
- HWP·PDF 내부 자료는 자동 변환하지 않는다(텍스트 등록만 가능)
- 대화 보존 기간 정책과 삭제 기능이 없다(D11)
