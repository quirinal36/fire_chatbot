## 4.2 도면 인식 AI 고도화 조사 (2026-09-19)

도면 인식을 "완성도 높은" 수준으로 올리기 위해 AI 를 어디까지 참여시킬지 조사했다. 결과는 [plan-ai-roadmap.md](plan-ai-roadmap.md).

- **실패의 주원인은 AI 가 아니라 방 나누기 알고리즘**(문 폭 1.3m 전역 닫힘, `frontend/src/plan/rooms.ts`)이다. 실제 도면 2장을 파이프라인에 넣어 확인했다. 아파트 도면(ex01)은 치수선으로 축척을 맞춘 상태에서 방이 2개만 나오고 바닥의 28.5% 가 어느 방에도 들어가지 않는다.
- 권고: 0) 실제 도면 평가셋 20장·안전장치 → 1) 방 나누기를 개구부 후보 기반으로 재설계하고 AI 가 후보를 판정 → 2) 원본 보존·크롭 배치·성분 ID 로 AI 입력 품질 개선 → 3) Gemini 폴리곤·MobileSAM 은 실험으로. 전용 학습 모델·앙상블은 보류.
- 진단 도구: `tools/plan3d/diag-rooms.ts` (브라우저와 같은 코드를 Node 에서 돌려 그림으로 남긴다).
- **평가셋 (2026-09-19 저녁)**: 의뢰자가 받아 둔 AI Hub 건축 도면 데이터로 평가셋 69장(벽·문·창 31, 공간 38)을 만들고 기준선을 쟀다(`tools/plan3d/build-eval.ts`·`eval-plans.ts`). 벽 F1 62%, 개구부 F1 22%, 맞힌 방 26%, 미배정 31%. **평가셋이 새 병목을 드러냈다 — 벽 두께 추정이 상세 도면에서 무너져(정답의 1/4) 열림이 무력해진다.** 자세한 것은 [plan-ai-roadmap.md](plan-ai-roadmap.md) 진행 기록.
- **승인 후 진행 (같은 날)**: 0단계 안전장치와 1단계(개구부 후보 기반 방 나누기)를 구현해 main 에 넣었다.
- **AI 검토를 없앴다 (2026-09-19, 의뢰자 결정)**: 인식 결과를 시각 LLM 이 보고 고칠 곳을 제안하던 단계를 제거했다. 평가셋으로 재 보니 구획 오류의 주원인은 검토가 메울 수 있는 것이 아니라 벽 두께 추정과 방 나누기 알고리즘이었고, 제안에 오판이 섞여 사용자가 매번 골라야 했으며, 검증 장치가 화면 코드의 3할을 차지했다. **자동 치수 읽기는 남겼다** — 모델이 판단하지 않고 도면에 적힌 숫자를 읽기만 하며 알고리즘이 검증할 수 있고, 참값 대비 0.1% 로 확인됐다. 까닭은 [plan-3d-guide.md](plan-3d-guide.md) 8.0 절.

## 4.3 도면 탭 배치 재설계 (2026-09-20)

의뢰자가 Aside 로 화면을 다시 보고 "도면 비율이 작다, 위쪽 버튼이 정신없다, 바닥 면적이 화면 밖, 단계 안내가 조작과 따로 논다" 고 했다. 세 관점의 독립 설계를 심사해 **단계 칩이 곧 도구판** 안을 채택하고 반영했다(UX-008, [plan-ui-ux-issues.md](plan-ui-ux-issues.md)).

- 760px 패널에서 캔버스 320px(37%) → 587px(70%), 크게 보기 91%. 바닥 면적 띠는 sticky 로 항상 화면 안.
- 칩 4개가 도구 카드의 탭. 주 행동을 마치면 다음 단계로 넘어가고 도착한 버튼이 맥동한다. 되돌리기는 캔버스 왼쪽 위.
- 회귀: plan-ux 21/21 · plan-layout 18/18(360/440/760) · plan-openings 6/6 · 타입 검사·단위 시험 86개.
- 남은 것: 초보자 1명 5분 시험, 1280×800 수동 확인, 머리글은 그대로.

## 5. 알려진 한계

- 조건을 빠뜨린 요약처럼 의미 수준의 답변 오류는 형식 검증으로 다 막지 못한다. 담당자 검수와 오류 신고로 보완한다
- 좁은 화면에서 대화 목록을 열 수 없다
- DB가 뭄바이 리전이라 질문당 약 1초가 더 걸린다
- HWP·PDF 내부 자료는 자동 변환하지 않는다(텍스트 등록만 가능)
- 대화 보존 기간 정책과 삭제 기능이 없다(D11)
